teardrop docs

Everything you need to install teardrop, read your stats, and submit your hours for review.

Quick start

  1. Install teardrop with the command for your OS below.
  2. Answer the questions teardrop setup asks. Saying yes to each is the recommended setup.
  3. Use Claude Code, Codex, or Amp as you normally do.
  4. Run teardrop for your timeline, or teardrop dashboard for charts.
  5. To see every computer's hours in one place, sign in to the dashboard and connect each one.

Install

macOS, Linux, and Git Bash on Windows

curl -fsSL https://raw.githubusercontent.com/part-avocado/teardrop/main/install.sh | sh

Windows (PowerShell)

irm https://raw.githubusercontent.com/part-avocado/teardrop/main/install.ps1 | iex

The installer downloads the right binary, checks it against the release's checksums.txt, and installs it without admin rights to ~/.local/bin, or %LOCALAPPDATA%\Programs\teardrop on Windows. It adds that folder to your PATH, then runs teardrop setup. Open a new terminal afterwards so the PATH change applies.

To update later, run teardrop update, or run the install command again. teardrop update v0.5.0 installs one version in particular. Once a day, a background sync checks for a newer release, and teardrop prints one line when there is one; teardrop never updates itself. These optional environment variables change what the installer does:

VariableEffect
TEARDROP_VERSIONInstall a specific release, such as v0.1.0.
TEARDROP_INSTALL_DIRInstall to another folder.
TEARDROP_NO_MODIFY_PATHDon't edit your shell profile or PATH; print the line to add instead.
TEARDROP_NO_SETUPDon't run teardrop setup afterwards.

With Go 1.25 or later you can also run go install github.com/part-avocado/teardrop/cmd/teardrop@latest.

teardrop setup

teardrop setup shows every place teardrop looks for logs, how many sessions it found, and when the newest one is from. Then it offers to:

  • Keep Claude Code history. Claude Code deletes transcripts after 30 days by default. Setup offers to raise cleanupPeriodDays to 3650.
  • Add Claude Code hooks for real-time capture. See Claude Code.
  • Add the Amp plugin. See Amp.

To set up one tool only, name it: teardrop setup amp, teardrop setup claude, or teardrop setup codex. Setup offers the Amp plugin even on a computer where Amp isn't installed yet, so it is in place when Amp is.

Note

Setup never changes anything without a yes. It keeps your own hooks and settings, saves a backup the first time it edits a file, and is safe to run again. Pass -yes to accept everything without prompts.

The report

Run teardrop to see the last 7 days, or teardrop -since 30d for longer. The first table lists work blocks; the second totals each project. Add -l (or --live) to keep it on screen and update it as you work; press Ctrl-C to quit.

ColumnMeaning
ENGAGEDTime you were plausibly involved. This is the number that matters.
SPAN / SESSION TIMEWall-clock time from first to last activity, for comparison.
PROMPTSPrompts you sent that counted.
SKIPPEDPrompts that earned no time. Under the table, the report says how many each check below skipped.
TOKENS IN/OUTTokens the model read (cached ones included) and wrote.
TOOLSWhich AI tools you used in that block.

A project is identified by its git remote, then its repository folder, then its working folder, so the same repo adds up across tools and clones. A folder in your home folder is written from it, as ~/code/app (and your home folder itself as home), so the key your site sees doesn't name your account on the computer. Projects that were keyed by their full folder before teardrop did this show up twice on your site: the old key holds the time from before, the new one the time since, and no time counts twice. Add -json to get the report as data.

The dashboard

The dashboard shows an activity heatmap, daily totals, projects, tools, and recent work blocks. There are two ways to open it.

The graphs are interactive. Hover a day, bar, or tool for the details. Click a day on the heatmap, or a bar, to list that day's work blocks (a week, on the yearly chart). Click a project in the table to see only that project; every number and chart follows it. Click again, or the chip at the top, to clear it.

On the website, with an account

The dashboard on the website adds up the hours from every computer you code on. Only you and your server's reviewers can see the dashboard; your public profile shows a summary to anyone.

  1. Open the dashboard and sign in with Hack Club. Your first sign-in creates your account.
  2. Run the two commands it shows: one installs teardrop, the other connects that computer to your account.
  3. Keep working. The page fills in as soon as the first sync arrives, and teardrop syncs again each time a reply finishes in Claude Code or Amp, or you stop one. Run teardrop sync to update it right away.

Settings has the rest:

PaneWhat it's for
SetupThe commands to connect another computer, and a button to make a new sync key if yours gets out.
ComputersEach computer that syncs to you and when it last did. Remove one to drop its hours.
DataUpload a stats file from a computer that can't reach the website (make it with teardrop export -o stats.json, and upload it within 7 days), or download a copy of everything the site holds about you.
AccountYour name, Slack ID, and member-since date from Hack Club Auth, sign out, and deleting your account. Deleting removes every computer and all of your stats from the site.

You can sign out from the menu at the top right of any page. A computer syncs to one account. To move it to another, remove it under Computers first.

On your computer, without an account

Run teardrop dashboard to open the same charts with live data from this computer, refreshed every 30 seconds. It runs on localhost only and refuses requests from other sites, so your stats never leave your computer.

Your public profile

Every account has a public profile at /@handle, which anyone can open without signing in. It shows your handle, the month you joined, your hours in the past year, a year of days, and your projects. It never shows your name, your Slack ID, or a folder on your computer. A project that is a repository on a public host, such as github.com/you/site, is named and linked; any other project is only counted, as one of your other projects. Under Settings, Profile, you can change your handle, hide or name each project, or make the profile private. A private profile, like a banned or deleted account, answers "no such profile", so its address doesn't say that the account exists.

Each account starts with a neutral handle, such as u-3f9a0c12b4d1, never one made from your name. When you change it, the old address stops working.

Verification keys

Every sync and export carries a verification key: an Ed25519 signature, made by your account, over the report's numbers, the time it was made, and the time it expires. Change one minute of engaged time, the account, or a date, and the key no longer matches. The website refuses a report that:

  • has no key, or a key that doesn't match its contents;
  • is more than 7 days old, so an old or reused file can't stand in for current numbers;
  • claims to be made in the future, or contains activity after the time it was made.

Each computer's key is created the first time it syncs or exports and kept in teardrop's data folder as account.key. Settings lists your computers by the ID of that key, such as td-4283292a8f76.

Warning

Verification proves a file wasn't edited after teardrop export made it. Because the account key lives on your computer, a file alone can't prove the numbers are real. For hours that count, use teardrop submit: the site credits only time whose records reached it as it happened.

What counts

teardrop counts the time you spend working with your AI tools: writing prompts, reading replies, and steering the agent. An agent left running on its own doesn't earn time, and parallel sessions on one project count once. Prompts that don't reflect real work aren't counted; they're listed as SKIPPED, with how many each of these checks skipped:

  • Keyboard mashing. A prompt where more than half the words look typed at random rather than written: no vowels, one key held down, a few keys over and over, or letters in an order no language uses. Words in any language count as writing, with or without their accents, and so do code and file names.
  • Repeats. Asking for nearly the same thing a third time within your last 5 prompts. The first two asks count.
  • Steering only. A third prompt in a row that only steers, such as "continue", "yes", "fix it", or "still broken". The first two count, and any prompt that asks for something new starts over.

The report says how many prompts each check skipped, not which prompts.

The rules, applied to each session's prompts and agent output in time order: before a prompt, the last 5 minutes of the gap count (reading the reply, writing the prompt); while the agent works, the gap counts as long as it lies within 10 minutes of your last prompt. Work blocks closer than 15 minutes are shown as one. Time between prompts beyond those caps isn't counted, and commits earn no time. Your site stamps each day's totals with the version of these rules (currently 1), and keeps every record, so a day can be counted again if the rules change; what a past submission was credited never changes.

teardrop calibrate shows how the caps treat your own logs: how long your gaps before prompts and before agent output are, how many run past the caps, and your engaged total under other caps. It reads only your computer's logs and uploads nothing. Two things differ between your site and the local count: time on two computers at once counts once on your site, and a Claude Code reply you interrupt runs no hook, so its end reaches your site late and up to 10 minutes of it is unwitnessed.

Tokens

Token counts come from the usage records Claude Code and Codex save with each response. A Claude Code response that's written several times, or copied into a resumed session, counts once. Codex counts are taken from the increase in its running totals. Amp counts come from the usage Amp hands the teardrop plugin when a turn ends, so they start with teardrop v0.6.0: Amp turns recorded before that show no tokens.

Claude Code

teardrop reads transcripts from $CLAUDE_CONFIG_DIR (which may list several folders), ~/.claude, and ~/.config/claude. It tells your prompts apart from tool results, compaction summaries, background notices, and subagent messages.

With hooks installed, Claude Code runs teardrop hook claude-code when a session starts or ends, when you send a prompt, and when Claude finishes. Each run appends one line to a local journal: the time, session, folder, and the prompt's word counts and fingerprint, never its text. If Claude Code deletes a transcript, the journal still has that session.

Codex

teardrop reads rollouts from $CODEX_HOME or ~/.codex, in both sessions and archived_sessions, including compressed .jsonl.zst files. It handles both the older and the current (0.147 and later) log formats. Subagent and reviewer sessions never count as your prompts.

teardrop setup also adds hooks to ~/.codex/hooks.json, so each prompt and turn end reaches your site as it happens, and a notify line to ~/.codex/config.toml, which syncs when a turn ends. Codex skips new hooks until you trust them: open Codex, run /hooks, and trust teardrop's. The notify line needs no trust step, so Codex syncs on its own either way. If your config.toml already has a notify program, teardrop leaves it alone.

Amp

Amp keeps threads on its servers, so teardrop setup (or teardrop setup amp for Amp alone) offers to write a plugin to ~/.config/amp/plugins/teardrop.ts. It records when a thread starts, when you send a prompt, and when Amp finishes, in the same journal as the Claude Code hooks. New Amp threads load it automatically; in open ones, run plugins: reload.

Threads in Amp's cloud

Threads you start in the Amp app or on ampcode.com run in Amp's cloud, not on your computer, so that plugin can't see them. A second plugin, teardrop-cloud.ts, counts them. It goes in your personal Amp plugins, which Amp loads in every cloud thread.

  1. On your teardrop site, open Settings, Setup, and choose Amp under “Check your tools”.
  2. Paste the prompt shown there into any Amp thread. Amp adds the plugin and two values to its Secrets & Env Vars settings: TEARDROP_SERVER, your site's address, and TEARDROP_KEY, your sync key. Amp asks you for the key in a private dialog, so it stays out of the thread.

In a cloud thread, the plugin downloads teardrop, checks it against the release's checksum, and runs it when you send a prompt and when Amp finishes. Each run sends your site one line: the time, thread, folder, repository, and the prompt's word counts and fingerprint, never its text. Your site keeps these lines for a year.

No computer of yours is needed. When Amp finishes a turn or you stop it, the teardrop in that thread reads all of your cloud lines back from your site, counts them with the same rules as everything else, and syncs the result. Threads that ran side by side are counted together, so their overlap counts once. Your cloud threads show up as one entry under Settings, Computers, named “Amp cloud threads”.

Note

Cloud time reaches your dashboard when Amp finishes a turn or you stop it. Its days are split at midnight UTC, because a cloud thread doesn't know your time zone. The Mac app's threads can also run on your Mac instead of the cloud: open the app's App Settings, Runner, turn it on, and pick “This Mac” when you start a thread. Those are recorded by the first plugin.

Set up with a prompt

The dashboard's setup steps include a prompt to paste into Amp or Claude Code, with your server already filled in. The agent installs teardrop, runs teardrop setup -yes to add the hooks and the plugin without stopping to ask, runs teardrop login and shows you the code to type on the site, and shows you the result. -yes is the part an agent can't do on its own, since setup otherwise asks before changing any settings. The prompt holds no key, so nothing secret ends up in that thread.

Copilot and Cursor

teardrop setup writes ~/.copilot/hooks/teardrop.json for GitHub Copilot CLI and VS Code's Copilot agent, and adds teardrop's hooks to ~/.cursor/hooks.json for Cursor, keeping any hooks of your own. Restart Cursor to load them. Neither keeps transcripts teardrop can read, so their time comes from the hooks alone, and only reaches your site when one is set up with teardrop sync.

OpenCode

teardrop setup (or teardrop setup opencode) writes a plugin to ~/.config/opencode/plugins/teardrop.ts, or the plugins folder of $OPENCODE_CONFIG_DIR when that is set. OpenCode 1 and 2 both load it. It runs teardrop hook opencode when you send a prompt and when a turn ends, finished, failed, or stopped, recording the time and folder, never the prompt text. Prompts in a subagent's session come from the agent, so they aren't counted as yours. OpenCode keeps its history in a database teardrop doesn't read, so time before the plugin was added doesn't count.

Add your own harness

Any tool can report to teardrop. Run teardrop hook <tool>, where the tool name is lowercase letters, digits, and dashes, with one JSON object on stdin:

{"session_id": "abc123", "cwd": "/home/me/project", "hook_event_name": "prompt", "prompt": "add a login page"}
FieldMeaning
session_idRequired. One conversation or thread.
hook_event_nameRequired, or pass -event: prompt, turn_end, session_start, session_end, or edit.
cwdThe folder, which names the project by its git remote. Only the project key leaves the computer.
promptFor prompt: scored for effort and repeats on the computer, then thrown away. Its text is never stored or sent.
tokens_in, tokens_out, lines_added, lines_removedOptional, on turn_end or edit.

teardrop always exits 0 and prints nothing, so it never gets in the tool's way. It writes the event to the local journal, and, once the computer is connected, sends it to your site as it happens. Your site credits only time whose records reached it within 5 minutes of when they happened. teardrop hook -check <tool> prints the record a payload would make and writes nothing, for testing an adapter.

For a tool with a hooks file in Claude Code's shape, point its prompt and stop hooks at teardrop hook mytool. For a tool with plugins, run the same command from the plugin, as teardrop's own Amp plugin does with teardrop hook amp.

Lines of code

When a computer syncs, teardrop also sends your site one record per commit of yours in each project with a git remote: its SHA, author time, and lines added and removed, never its message or code. Commits earn no time. Your profile links a public repository's latest commits, and once an hour the site asks GitHub which of them exist, so a reviewer can tell a claimed commit GitHub doesn't have. For each commit GitHub has, the review app also shows the GitHub account it is linked to, and marks one whose claimed time differs from GitHub's author date: the SHA pins that date, so a difference means the time was changed after the commit was made. A private repository's commits are shown as not checked. The check needs a GITHUB_TOKEN secret on the Worker; without one, the review app says so.

For each project the report shows the lines agents changed (AGENT LINES), how many of the added lines later turned up in your commits (KEPT), and the lines your own commits added (COMMITTED). The code itself is not kept.

Sync and submit

teardrop sync sends your account records: one per prompt and turn end, with its time, word counts, tokens, and lines, never its text. The first sync sends the past year; later ones send only what changed. Turns your hooks already sent count as witnessed; turns from transcripts that no hook saw reach the site late and are shown but not credited. The first time, connect the computer:

teardrop login -server https://your-site

It prints a code such as BCDF-GHJK and opens the site's connect page; sign in, type the code, and check that the computer ID it shows matches the one in your terminal. teardrop then saves the key and syncs. A code lasts 10 minutes and works once. It has to be typed rather than followed from a link, so nobody can send you a link that connects their computer to your account. On a computer with no browser, teardrop sync -server https://your-site -key tdk_…, with the key from Settings, does the same.

teardrop remembers the server and the key, so later it's just teardrop sync, and hooks sync in the background when a reply finishes or you stop one. Amp reports a stopped reply at once; Claude Code runs no hook then, so that sync happens at your next prompt or when the session closes. Codex syncs through its notify program when a turn ends. The key can only upload stats. If the server answers that it needs your sync key, run teardrop login again.

teardrop submit <project> asks your site to submit a project. Nothing is uploaded: the site makes the submission from the per-prompt records your hooks already sent it. Only time whose records reached the site within 5 minutes of when they happened is credited. Time that arrived late, such as history from before your hooks were set up or work done offline, is listed but not credited unless a neoadmin accepts it. A reviewer approves, adjusts, or rejects each submission, with a note you read. A rejected submission credits nothing, and its time stays covered, so submitting again won't credit it. You can submit a project again as it grows; time an earlier submission already covered is credited once.

You can also submit from your dashboard: each project has a Submit button, with room for a note to the reviewers. The dashboard's Submissions list, and teardrop submit -list, show each submission's credited, unwitnessed, and accepted time, whether it is still waiting or was approved, adjusted, or rejected, what it finally credits, and the reviewer's note. They don't say which reviewer decided.

Witnessing stops backdating and editing after the fact. It can't stop a script that sends made-up records live, which no tracker on your own computer can rule out, so reviewers also see flags: more than 16 witnessed hours in a day, gaps between prompts that barely vary, prompts the agent never answered, and Amp turns with no tokens.

Your stats on the website are visible to you and to reviewers, apart from what your public profile shows: a reviewer sees, for each project, your total and a timeline of your work blocks (when each started and ended, with its prompts, tokens, and lines changed), and neoadmins and superadmins see everything you synced. Deleting your account, under Settings, removes them; admins keep your Slack ID and a record of what your computers reported, without project names. Submissions hold no chats; reviewers see their records in the review app. To host the site, see Running a server.

Running a server

The site is one Cloudflare Worker with a D1 database for summaries, an R2 bucket for every report and per-prompt record, and a Durable Object per account that takes records as they arrive and pushes them to open dashboards.

The website, on Cloudflare

The Worker is in the worker folder of the repository and serves the pages in site. You need a Cloudflare account and Node.js 22 or later.

To try it on your computer first:

cd worker
npm install
cp .dev.vars.example .dev.vars
npm run dev

.dev.vars signs every visitor in as the Slack user ID in DEV_LOGIN, which only works on localhost. Open the address it prints and follow the setup steps on the dashboard.

To put it online, connect the repository to Cloudflare. Nothing needs to be installed or signed in on your computer.

  1. In the Cloudflare dashboard, open Workers & Pages, then Create, then Import a repository. Choose your fork of the repository.
  2. Name the Worker teardrop, set the root directory to worker, the build command to npm ci, and the deploy command to npm run deploy. Save and deploy. The first deploy creates the D1 database, its tables, and an R2 bucket that keeps every report for reviewers. It runs without the secrets, and the site says it is not set up yet.
  3. Create a Hack Club Auth app as in Set up sign-in below, with the openid, profile, and slack_id scopes and https://<worker>.<your-subdomain>.workers.dev/auth/callback as its redirect URI. Cloudflare shows the address under the Worker's Settings, Domains & Routes.
  4. Under the Worker's Settings, Variables and Secrets, add these as secrets: SESSION_SECRET (any long random text), HCA_CLIENT_ID, HCA_CLIENT_SECRET, and ADMINS. Deploying again, which a push to the branch does, keeps them.

The bucket needs R2 turned on for your Cloudflare account, which you do once under R2 in the dashboard. If the build fails on permissions for D1 or R2, open the Worker's Settings, Builds, and give its API token D1 Edit and Workers R2 Storage Edit access.

To deploy from your computer instead, run npx wrangler login in worker, then npm run deploy, and add the secrets in the dashboard or with npx wrangler secret put <NAME>.

SettingMeaning
SESSION_SECRETSigns sign-in cookies. Changing it signs everyone out.
HCA_CLIENT_ID, HCA_CLIENT_SECRETYour Hack Club Auth app.
ADMINSSlack user IDs of the superadmins, separated by commas. They add everyone else who reviews, in the review app.
GITHUB_TOKENOptional secret. Lets the hourly check ask GitHub which claimed commits exist, when GitHub dates them, and whose they are. Without it, commits are linked but not checked, and the review app says so.
MIN_VERSIONOptional variable, such as v0.6.0. Older teardrops, and ones too old to say their version, are told to run teardrop update and can't sync until they do. Their records wait on their computers and arrive late, so late that their time isn't credited, so raise it only for a fix that needs it. Empty answers every version.
UPLOAD_BURST, RECENT_RECORDS_PER_DAY, OLD_RECORDS_PER_DAYWhat one account may send: 1,000 uploads at once, which come back one a second; 30,000 records a day dated in the last two days; and 1,000,000 older ones a day, for a first sync of a year. Past one, the site answers 429 and teardrop keeps the records to send later. The defaults are about ten times the heaviest honest use. Records held back more than 5 minutes arrive late and aren't credited, so lower them with care.

To change a secret later, edit it in the dashboard. For your own domain, add a custom domain to the Worker and use it in the redirect URI. Cloudflare accepts uploads of up to 100 MB.

The review app

Reviewing has its own app at /review/, apart from the rest of the site. Reviewers get a Review link in the top bar. What a reviewer can do depends on their level:

LevelWhoWhat they can do
SuperadminThe Slack IDs in ADMINS.Everything below, and add or remove neoadmins.
NeoadminAdded by a superadmin.Read every account: its computers, its projects, and a log of every report it sent. Each log entry shows what the report held and which days and projects changed, and links to the report itself, kept as it arrived. Add and remove reviewers. Ban people. Accept unwitnessed time, adjust what a submission credits, and decide a submission again.
ReviewerAdded by a neoadmin or superadmin.Look a person up by Slack ID and read their total for each project, with each project's graphs. Approve or reject a waiting submission. Nothing else of theirs.

To add someone, look up their Slack ID in the app and choose a level in the Access panel of their account view. They can be added before they first sign in. No one can add, remove, or ban someone at their own level or above, so a neoadmin can't touch another neoadmin.

Each person's page has a Project activity panel. For one project at a time it draws engaged time and lines added and removed per day, when in the week they work, and every work block's length against the share of it that was engaged. It also checks the blocks for what to ask about: time counted on two computers at once, long blocks without breaks, lines changed without a prompt, very many lines per hour, and days over 14 hours. A check that stands out is a reason to ask, not proof.

Levels and bans are set on a person's account view, in its Access and Bans panels. A Slack ID that has never signed in opens a view with only those two, so a person can be added or banned before their first sign-in. The Reviewers and Bans pages list who holds each level and every ban, and link to each account view.

A ban has no length: it lasts until someone lifts it, and always has a reason, which only reviewers see. While it holds, the site takes nothing new from the person: no syncs, uploads, cloud events, or submissions. teardrop sync, their dashboard, and their settings say plainly that they are banned until a reviewer lifts it, but not why. They can still sign in and see what they had. The review app marks a banned person in red wherever they appear. A banned reviewer can't review. Someone below the level of whoever issued a ban can't lift or replace it.

Any reviewer can make API keys, under API keys in the app, for a script or a bot. A key acts as the person who made it, at the level they hold when it is used, and stops working when they are removed or banned. The key is shown once, in a popup to copy it from; the site keeps only its hash. Send it as a bearer token:

curl -H "Authorization: Bearer tdr_..." "https://your-site/api/review/person?slack=U012ABCDEF"

Public API

Anyone with an account can read their own stats from a script, or let another site read them, for example to list your projects when you sign in there. Make a read key under Settings, API. It starts with tdp_, is shown once, and can only read: it can't upload, change, or delete anything. Your sync key doesn't work here, and a read key doesn't sync. While your account is banned, your read keys read nothing.

curl -H "Authorization: Bearer tdp_..." "https://your-site/api/public/v1/projects"
CallWhat it returns
GET /api/public/v1/mename, slack_id, created_at, engaged_seconds in the past year, and synced_at.
GET /api/public/v1/projectsprojects, most time first, each with name, repo (such as github.com/you/site, or null for a project that is only a folder), engaged_seconds, first_active, and last_active.
GET /api/public/v1/days?since=2026-01-01days: each date with its engaged_seconds. since is optional.
GET /api/public/v1/users/{handle}Anyone's public profile, with no key: handle, joined (YYYY-MM), engaged_seconds in the past year, days, projects (each with name, repo, and engaged_seconds), and other_projects (count and engaged_seconds). A private, banned, or unknown profile answers 404. Answers may be cached for a minute.

Times are Unix milliseconds. Answers are JSON; a refusal is plain text with its reason. Any site may call the API from the browser, since it takes only the key and no cookies. Folders on your computer are never shown, only repositories.

Sign in with teardrop

A site can get a read key without anyone pasting one. Send the person to:

https://your-site/authorize?redirect_uri=https://example.com/callback&state=RANDOM&name=My+portfolio

They sign in if they need to, see the site's address and what it will read, and choose Allow. They come back to redirect_uri with code and your state, or with error=access_denied if they cancel. Check that state is the one you sent, then trade the code within 5 minutes, from your server or the browser:

curl -X POST https://your-site/api/public/v1/token \
  -d '{"code":"tdc_...","redirect_uri":"https://example.com/callback"}'

The answer is {"key": "tdp_...", "token_type": "Bearer", "name": ..., "slack_id": ...}. Use the key with the calls above. A code works once, for the redirect_uri it was made for; trading it a second time also revokes the key it became. redirect_uri must use https, except on localhost. A site without a server should add PKCE: send code_challenge, the base64url SHA-256 of a random verifier, and send code_verifier with the code. The key shows under the person's Settings, API, named after your site, where they can revoke it. Each site keeps at most 5 keys per person; signing in again after that revokes the oldest. Banned accounts can't sign in.

Set up sign-in

  1. Open Developer Apps on auth.hackclub.com and create an app with the openid, profile, and slack_id scopes.
  2. Add https://your-site/auth/callback as its redirect URI.
  3. Copy the app's client ID and client secret into the Worker's secrets.
  4. Collect the Slack user ID of each superadmin for ADMINS: in Slack, open their profile, choose ⋮, then Copy member ID.

Moving from the old review server

teardrop v0.6 and before submitted chat logs to a separate Go review server. It is retired: submissions are now made on the site from the records it holds. To keep what it credited, so no project is credited twice, run teardrop export-records -data <its data folder> > records.jsonl and, as a superadmin, post the file to /api/review/import. Each record is matched to its account by the computer that sent it.

Hosting cost

node worker/scripts/cost-model.ts [prompts per hour] prints the monthly bill from named inputs, with Cloudflare's prices of 2026-11-22. For 15,488 people logging 109,759 engaged hours a month at 20 prompts an hour, it comes to about $10 a month after a year and $13 after three ($27 and $35 at 60 prompts an hour), against a $500 limit. Every record, every report, and the account log's older rows are kept in R2 for good; D1 keeps each person's newest few hundred log rows and the day totals, which pass D1's 10 GB limit in about year 6 unless old days are folded into months. The inputs are assumptions until measured against a real deploy.

Privacy

teardrop reads timestamps, token counts, line counts, and working folders from your logs. Prompt text is only scored in memory to count recognized words; it is never stored or printed, and sync never uploads it. In Amp's cloud, the plugin sends your website each prompt's time, thread, folder, repository, and word counts, without its text, and every other harness's hooks send the same kind of record. The website keeps these records in R2 for good. The website keeps each report your computers send, which holds those counts and times, so reviewers can read it; deleting your account deletes them. Your public profile shows your hours, your days, and the projects it names to anyone, unless you make it private. Chat logs and prompt text never leave your computer.

To see exactly what leaves your computer, run teardrop sync -dry-run, which prints the records the next sync would send and sends nothing, or pipe a hook payload into teardrop hook -check <tool>.

Troubleshooting

Start with teardrop doctor. It checks the usual causes below and prints what to run for each one it finds.

“No Claude Code or Codex sessions found”

Run teardrop setup to see where teardrop looked. If your logs live elsewhere, such as inside WSL on Windows, pass -claude-dir or -codex-dir. Try -since 30d if your last session was more than a week ago.

“teardrop: command not found”

Open a new terminal so the PATH change applies. On Windows, restart any terminal that was open during install.

“skipped N log files that could not be read”

Run teardrop -verbose to list them. Usually they are files a tool is still writing, and the rest of the report is unaffected.

“Your clock is N minutes ahead of (or behind) the site's”

The site credits a record only when it arrives within 5 minutes of the time it says it happened, and refuses records dated more than 5 minutes ahead of its own clock. A computer clock that is off by more than that loses all its time, so teardrop sync compares the two and warns from 2 minutes off. Turn on setting the time automatically in your system's date and time settings, then sync again.

My hours look too low or too high

Compare ENGAGED with how long you think you worked, and please open an issue with the numbers.

Uninstall

teardrop uninstall

It asks once, then removes teardrop's hooks from Claude Code, Codex, Cursor, and Copilot, its Amp and OpenCode plugins, and the line the installer added to your shell profile (on Windows, the folder it added to your Path), leaving your other settings and lines as they were. It asks whether to keep the journal folder, which holds this computer's account key and any records not sent yet, and deletes the binary last. Windows can't delete a running program, so there it tells you to delete teardrop.exe once the window closes. -yes answers every question, deleting the journal folder unless you add -keep-data.

Your account on the site keeps what it has; remove the computer under Settings, Computers. Claude Code's longer history setting and teardrop's .teardrop-backup copies of settings files stay. To remove only the hooks and keep teardrop, run teardrop setup -remove-hooks.
